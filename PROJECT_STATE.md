# PROJECT_STATE

## Overview
`kai` is a local-first desktop AI chat app: Tauri 2 shell, React 19 + TypeScript + Tailwind 4 frontend, Rust backend, SQLite storage, and a local Ollama server (`http://127.0.0.1:11434`) for generation. There is no hardcoded model: generation uses whichever row in the cached model catalog is marked active.

## Stack
- Frontend: React 19, TypeScript (strict), Vite 8, Tailwind 4, Zustand 5, react-markdown + rehype-highlight.
- Backend: Tauri 2, tokio, reqwest, rusqlite (bundled) + rusqlite_migration, thiserror.
- Storage: SQLite file `kai.db` in the app data dir, WAL mode, foreign keys on.

## Commands (verification)
Frontend (project root):
```
npx tsc --noEmit      # typecheck
npm run build         # typecheck + production bundle (tsc && vite build)
npm run dev           # Vite dev server on port 1420
npm run tauri dev     # desktop app (runs npm run dev first)
npm run tauri build   # production binary + installers in src-tauri/target/release/bundle/
```
Backend (`src-tauri/`):
```
cargo check           # typecheck
cargo build           # build
cargo test --lib      # backend unit tests
```
Backend unit tests live in `state.rs`, `services/chat_service.rs`, `services/model_service.rs` and `database/repository.rs`. The DB-backed tests open `Connection::open_in_memory()`, enable foreign keys and apply the real migration set through `database::init::migrate`. The repository tests cover history create/touch/title/list ordering, branch creation and active-branch selection, branch head updates, message insert/chain loading, `delete_last_message`, `get_variants`, `get_nth_message_id`, the model catalog (`get_models`, `replace_models` incl. the single-active index) and FTS `search_history` (titles and user messages only, multi-token AND, quote stripping, blank-query fallback, cleanup on delete). The chat service tests cover the DB-backed flow (`record_user_message`, `load_chat`, `switch_branch`, `delete_chat`, `new_chat`, `persist_assistant`) and the streaming/finalize helpers (`LineBuffer`, `parse_line`, `apply_chunk`, `consume_stream` with a fake byte stream, `finalize_generation` for done/cancelled/eof/error). The model service tests cover the non-network paths: `active_model`, `set_active_model` (switch, unknown name rollback), `sync_if_empty` when the catalog is already populated, and `cancel_download`. The attachment service tests cover extension classification (including an unsupported type) and the base64 encoder's padding; the repository tests cover storing and reloading a message's attachments. `attachment_service::attach` (file copy and limits) and `read_text` / `read_image_base64` are untested; the send-time vision rejection, the text/image expansion in `with_attachments`, the pending-attachment queue in `ChatSession` (add, take, remove by path including `AttachmentNotFound`, clearing on replace/reset) and the persistence of pending attachments in `record_user_message` are covered. `attachment_service::detach` is covered for deleting the copied file, tolerating a copy that is already gone, and leaving a file that is not queued alone. The cleanup paths are untested: `attachment_paths_for_history`, `attachment_service::discard`, the copy deletion in `load_chat` / `switch_branch` / `new_chat` / `delete_chat`, the pre-persist `validate_pending` check in `send`, the pending-queue restore when `insert_attachments` fails, and the attachment-name title fallback. Everything that calls Ollama (`generate`, `send`, `resend`, `edit`, `create_title`, `title_if_missing`, `sync_models`, `download_model`, `delete_model`) is untested because it needs the network. There are no frontend tests.

## Structure

### Backend — `src-tauri/src/`
- `lib.rs`: composition root. Initializes the DB pool (a failed initialization is returned from `setup` instead of panicking), manages `Mutex<ChatSession>`, registers all 21 commands, and syncs the model catalog from Ollama on startup when the `models` table is empty (emitting `models_changed` when it did).
- `commands/chat_command.rs`: Tauri boundary (the only layer with `AppHandle`). Commands: `send_message`, `resend_message`, `edit_message`, `load_chat`, `switch_branch`, `get_variants`, `new_chat`, `delete_history`, `cancel_generation`, `get_session`, `get_history`, `search_history`. Also maps `ChatEvent` to Tauri events.
- `commands/model_command.rs`: model catalog commands: `sync_models`, `download_model`, `cancel_model_download`, `delete_model`, `get_models`, `get_active_model`, `set_active_model`. `sync_models`, `delete_model` and `set_active_model` emit `models_changed`; `download_model` emits `model_download_progress` and resolves when the pull ends, whether it completed or was cancelled.
- `commands/attachment_command.rs`: `attach_file(path)` — resolves `app_data_dir` and forwards to `services/attachment_service.rs`, returning the stored `Attachment`; `remove_pending_attachment(path)` drops a queued attachment from `ChatSession`.
- `services/model_service.rs`: all model catalog logic — fetches `/api/tags` plus `/api/show` for each model (vision check), caches the result in the `models` table, preserves or falls back the active selection,   and resolves the active model for generation. `sync_if_empty` reports whether it had to sync. `download_model` takes the download token from `ChatSession::begin_download`, streams a pull from Ollama as `ModelDownloadProgress` events, then re-syncs the catalog and emits `ModelsChanged`; a cancelled pull returns `false` before re-syncing. `cancel_download` cancels the active token. There is no downloadable-model catalog: Ollama only lists installed models, so `download_model` takes any model name from the caller.
- `services/chat_service.rs`: all chat logic — persisting the user message, creating history/branches, streaming Ollama output, finalizing/cancelling generation, edit-as-fork, title generation. Before a request the outgoing messages are expanded by `with_attachments`: `.txt` attachments are read and appended to the message content as `\n\nAttached file:\n<text>`, images are read and base64-encoded into `ChatMessage::images`. The image path re-checks the active model's `supports_vision` at request time, so switching to a text-only model after attaching fails with `AttachmentNeedsVisionModel` before anything is sent. Pending attachments are persisted against the new user message in `record_user_message`. `send` validates the pending attachments first (vision support for images, readability for text) so a rejected attachment fails before anything is written, and `record_user_message` puts them back on the queue if `insert_attachments` fails. `load_chat`, `switch_branch` and `new_chat` delete the copied files of the pending attachments they discard; `delete_chat` deletes the copies of every attachment stored against that history's messages plus the pending ones.
- `services/attachment_service.rs`: attachment validation and storage. `attach` classifies the file by extension (`.png`/`.jpg`/`.jpeg`/`.webp`/`.gif` = image, `.txt` = text), rejects anything else, enforces 10 MB for images and 1 MB for text, requires an active model with `supports_vision` for images, rejects empty text files, copies the file into `<app_data_dir>/attachments` under a timestamped name, and queues it on `ChatSession` as a pending attachment. `read_text` / `read_image_base64` read a stored attachment back for a request; `detach` removes one from the pending queue by path, deletes its copied file (an already-missing copy is tolerated) and fails with `AttachmentNotFound` when it is not queued; `discard` deletes the copies of an iterator of paths on the same terms; the base64 encoder is in this module (no extra crate).
- `state.rs`: `ChatSession` — in-memory source of truth (`history_id`, `messages`, `active` stream + cancellation token, `next_generation_id`, `active_branch_id`, `download` cancellation token, `pending_attachments`) with `begin_generation`, `end_generation`, `begin_download`, `end_download`, `add_pending_attachment`, `take_pending_attachments`, `remove_pending_attachment`, `push_user`, `push_assistant_placeholder`, `append_content`, `append_thinking`, `pop_last_assistant`, `truncate`, `replace`, `reset`, `snapshot`.
- `models/ai_model.rs`: `AiModel` (stored model details + `supports_vision` + `active`) and Ollama `/api/tags` / `/api/show` payload types.
- `models/attachment_model.rs`: `Attachment` (`id`, `name`, `kind`, `mime_type`, `path`, `size_bytes`) and `AttachmentKind` (`Image` | `Text`) with `as_str` / `from_str`.
- `models/chat_model.rs`: `ChatMessage` (plus `attachments` and the request-only `images` base64 list, both omitted from JSON when empty), `Role` (`User` | `Assistant`), `SessionSnapshot`, `MessageVariant`, `GetHistory`, `ActiveStream`, Ollama request/response types.
- `models/chat_event.rs`: `ChatEvent` enum sent to the UI (tagged `type`): snapshot, deltas, generation finished, error, `HistoryChanged`, `ModelsChanged`, `ModelDownloadProgress`.
- `models/error_model.rs`: `ChatError`; serialized to the frontend as its message string. Ollama-specific variants carry the user guidance: `OllamaNotInstalled`, `OllamaNotRunning` and `ModelNotInstalled` (returned on a 404 from `/api/chat` or `/api/generate`).
- `database/init.rs`: opens `kai.db`, sets WAL + foreign keys, applies migrations. `migrate` applies the migration set to any connection (used by the tests with an in-memory DB).
- `database/repository.rs`: all SQL. Branch loading uses a recursive CTE from `branches.head_message_id` up through `parent_message_id`; `delete_last_message` moves the head to the new last message. Model catalog reads/writes: `get_models`, `replace_models`, `set_active_model`. Attachments: `insert_attachments` writes a message's attachments, `attachment_paths_for_history` lists a history's stored copy paths for cleanup, `load_branch` loads them back per message.
- `database/migrations/001_initial_schema.sql`: `historys`, `branches`, `messages`.
- `database/migrations/002_add_fts5.sql`: `history_fts5` virtual table plus triggers for history titles and `role = 'user'` messages.
- `database/migrations/003_add_models.sql`: `models` table plus a partial unique index allowing only one `active` row.
- `database/migrations/004_rename_historys.sql`: renames `historys` to `histories` and drops the unused `branches.name` column.
- `database/migrations/005_add_attachments.sql`: `attachments` table (`message_id` → `messages` with `ON DELETE CASCADE`, `name`, `kind`, `mime_type`, `path`, `size_bytes`, `created_at`) plus a `message_id` index.
- `ollama.rs`: single `OLLAMA_BASE_URL` (`http://127.0.0.1:11434`) plus an `endpoint` helper, and `transport_error`, which turns connect/timeout failures into `OllamaNotInstalled` or `OllamaNotRunning` after checking `PATH` and the default install locations (nothing is installed automatically). `post_chat` (streaming `/api/chat`), `post_generate` (`/api/generate`, used for titles), `get_tags` (`/api/tags`), `show_model` (`/api/show`), `pull_model` (`/api/pull`, takes a `CancellationToken` and returns `Ok(false)` when cancelled, streaming NDJSON progress to a callback, including a final line without a trailing newline; an `error` field, a non-JSON error body, or a stream that ends without the final `success` status becomes `ChatError::ModelDownloadFailed`), `delete_model` (`DELETE /api/delete`).

### Frontend — `src/`
- `App.tsx`: shell. Installs keymap + chat event listener, recovers session with `get_session`, renders `Home` when `messages.length === 0` and `Chat` otherwise, plus `InputBar`, `HistoryPanel`, `SideLabels`.
- `store/messages.ts`: chat state, the pending attachment list (`attachments`, cleared on every `Snapshot`) and model catalog state (`models`, `modelsVersion`) from the backend; the active model is the `active` row in `models`. `pickAttachments()` opens the native file dialog (`@tauri-apps/plugin-dialog`) filtered to the supported extensions and calls `attach_file` for each chosen path, continuing with the remaining paths when one is rejected. `loadModels` refetches when `modelsVersion` changes; `selectModel` switches the active model and closes the panel, `syncModels` re-syncs — both let `models_changed` drive the refetch. `chatReducer` handles `ChatEvent`; helpers `run` (invoke + error capture), `fetchVariants`, `refreshVariants`, `switchBranch`, `parentKey`.
- `store/ui.ts`: UI-only state — `mode` (`idle` | `compose` | `edit`), `overlay` (`history` | `models` | `downloads` | null), drafts, `editIndex`, `thinkingIndex`, history list/index/armed-delete/search, `modelIndex`, `downloadQuery`, `scrollPinSignal`. `getActiveLayer` resolves `overlay ?? mode`.
- `events/chatListener.ts`: maps Tauri events (`chat_event`, `update_snapshot`, `update_message_content`, `update_thinking_content`, `emit_done`, `chat_error`, `history_changed`, `models_changed`) into `useMessages.dispatch`.
- `keymap.ts`: every keyboard binding, scoped by active UI layer; `handleKeydown` dispatches.
- `components/`: `InputBar` (compose/edit textarea, pending-attachment chips, paperclip picker button, send/edit submit, error line), `MessageView` (user/assistant rendering, attachment chips on user messages, variant switching), `AttachmentChip` (shared attachment chip, removable when a remove handler is passed), `MarkdownMessage`, `ThinkingBlock`, `BranchNavigator`, `HistoryPanel` (overlay, FTS search on query change, delete confirm), `ModelPanel` (keyboard-only overlay, loads on `modelsVersion`, lists cached models with the active one marked), `DownloadPanel` (keyboard-only download overlay: model-name input plus progress bar), `SideLabels`, `Copy`, `Logo`.
- `pages/`: `Home.tsx` (centered logo), `pages/chat/Chat.tsx` (scroll container, bottom-pin scroll behavior, edit scrolling).
- `types.ts`: frontend mirrors of `Message` (including `attachments`), `Attachment` / `AttachmentKind`, `MessageVariant`, `SessionSnapshot`, `ChatEvent`, `Conversation`, `DownloadProgress`, `ModelInfo`.
- `App.css`: theme tokens, layout widths, overlay z-layers.

## Data flow
1. User input: `keymap.ts` (ctrl+m / ctrl+e) or `InputBar` → `invoke("<command>")` through `run()` in `store/messages.ts`.
2. `commands/chat_command.rs` forwards to `services/chat_service.rs` with the managed `ChatSession` and DB connection.
3. The service mutates `ChatSession`, persists through `database/repository.rs`, and calls Ollama through `ollama.rs`.
4. Progress is reported as `ChatEvent` → emitted as Tauri events → `events/chatListener.ts` → `useMessages.dispatch` → `chatReducer`.
5. Components read only from the Zustand stores; UI-only state lives in `useUI`, backend-derived state in `useMessages`.

## Data model
- `histories`: one row per conversation (`title`, `active_branch_id`, `created_at`, `updated_at`).
- `branches`: a conversation can have several; `parent_branch_id`, `fork_message_id`, `head_message_id` (head = last message in that branch).
- `messages`: `history_id`, `branch_id`, `parent_message_id`, `role` (`user` | `assistant`), `content`, `thinking`, `created_at`.
- `attachments`: files attached to one message — `message_id`, `name`, `kind` (`image` | `text`), `mime_type`, `path` (copied file inside `<app_data_dir>/attachments`), `size_bytes`, `created_at`; deleted with their message.
- `history_fts5`: FTS5 index over history titles and user-message content; used only by `search_history`.
- `models`: cached Ollama models — `name` (primary key), `family`, `parameter_size`, `quantization_level`, `size_bytes`, `modified_at`, `supports_vision`, `active` (exactly one row can be active). Rows are replaced on `sync_models`, so no Ollama call is needed to read the catalog.
- A conversation's visible messages are the chain from `branches.head_message_id` back through `parent_message_id`.

## Current features
- Streaming chat with Ollama including separate `thinking` deltas.
- Composer (`ctrl+m`) and in-place edit (`ctrl+e`, `ctrl+ArrowUp/Down` to jump between user messages).
- Edit forks a new branch from the previous message and regenerates; `BranchNavigator` switches between sibling variants.
- Resend last response (`ctrl+r`), cancel generation (`ctrl+s`, cancellation token).
- New chat (`ctrl+n`), history overlay (`ctrl+h`) with arrow/Enter selection, two-step delete (`ctrl+Delete` / `ctrl+Backspace`).
- Model picker (`ctrl+k`, keyboard only): overlay lists cached models with family, parameter size, quantization, disk size, modified date and a vision icon for image-capable models, with the active model marked; Enter or click switches, `ctrl+r` re-syncs from Ollama. The catalog refetches only when the backend emits `models_changed`.
- History search: server-side FTS5 over titles and user messages, requested on each query change; results from a superseded query are discarded. The search field stays visible while a query is active, so an empty result set ("No results") can still be edited or cleared.
- Model catalog: `sync_models` loads models from Ollama `/api/tags`, checks the `vision` capability per model via `/api/show`, and stores the details in SQLite; `get_models` / `get_active_model` read the cache, `set_active_model` switches models. `download_model` pulls any Ollama model by name with live progress and re-syncs the catalog; `delete_model` removes a model through `/api/delete` and re-syncs (backend only, no UI caller).
- Model download overlay (`ctrl+d`, keyboard only): type any Ollama model name, Enter starts the pull, and a footer bar shows status, percent and transferred size from `model_download_progress`; errors from Ollama appear in the panel. `ctrl+s` cancels the running pull (Ollama resumes the partial pull on the next attempt) and the bar clears when the command resolves. Starting a download clears the previous error, a download that ends, completes or is cancelled, clears the bar when the command resolves, and a failed or interrupted download reports the error and clears the bar, leaving the partial pull to resume on the next attempt. Nothing is fetched when the overlay opens. Chat and title generation use the active model, and `ModelPanel` drives all four commands. If the cache is empty, the first chat request syncs the catalog on demand and emits `models_changed`, so no manual refresh is needed.
- File attachments: the paperclip button in the composer opens the native file dialog (`@tauri-apps/plugin-dialog`, `dialog:allow-open` capability) filtered to `.txt` and image files, then opens the composer and calls `attach_file` for each chosen path, which validates and copies the file, rejecting an unsupported type, an oversized file, an empty text file, or an image when the active model has no vision support. Dropping files onto the window is not handled. Pending attachments appear as removable chips in `InputBar` (the × calls `remove_pending_attachment`, which also deletes the stored copy), can be sent without text, and are listed as chips on the persisted user message. The next `send_message` binds the attachments to that user message; `.txt` text is appended to the request content and images are sent as base64 to a vision-capable model. Attachments are validated before the user message is persisted, so a rejected image leaves no message behind. The copied files are deleted when the queue is discarded (remove, new chat, load chat, branch switch) and when a chat is deleted. An attachment-only first message titles the chat with the attachment names instead of calling the model.
- Title generation for a new conversation runs in a detached task after `send_message` resolves; the title arrives through `history_changed`.
- Session recovery on mount; branch selection persisted via `historys.active_branch_id`.
- Assistant messages support markdown, syntax highlighting, copy, and collapsible thinking.
- Frameless window (`decorations: false`) with drag region; ctrl+shift+m minimize, F11 fullscreen, ctrl+w close.

## Distribution
- `src-tauri/tauri.conf.json` sets product name `kai`, version `1.0.0`, identifier `com.aamen.kai`, bundle metadata (publisher, copyright, category, descriptions) and NSIS `installMode: currentUser`. `targets: "all"` resolves to NSIS + MSI on Windows and AppImage + deb on Linux.
- User data lives in the per-user app data dir (`%APPDATA%\com.aamen.kai\kai.db` on Windows, `~/.local/share/com.aamen.kai/kai.db` on Linux); migrations are compiled in with `include_str!`, so no data files ship next to the binary.
- `.github/workflows/release.yml` runs on `v*` tags: a `windows-latest` job builds `--bundles nsis,msi` and an `ubuntu-22.04` job builds `--bundles appimage,deb`, both uploading to a draft Release through `tauri-apps/tauri-action`. It uses only the built-in `GITHUB_TOKEN`.
- `@tauri-apps/api` is pinned to `~2.12.0` because the Rust `tauri` crate is `2.12.x`; `tauri build` refuses to bundle when the NPM package and the crate are on different minor versions.
- Ollama and models are deliberately not bundled; they are the user's responsibility, and the app only reports when they are missing.

## Known issues / open points
- `app.security.csp` is still `null`; a Content Security Policy has not been added.
- A database migrated by a newer build (`user_version` above 5, i.e. after a later migration) makes `database::init::init` fail; `setup` returns the error and Tauri aborts the process without any UI feedback. Fixing that needs a decision (native dialog dependency, or a data-version policy).
- `src/Logo.tsx` is unused and points at `/Screenshot_2026-09-19_003350-removebg-preview.png`, which does not exist in `public/`.
- No frontend tests; CI (`.github/workflows/cargo-test.yml`) runs `cargo test` in `src-tauri/` on every push, with build artifacts cached by `Swatinem/rust-cache`. Network-dependent chat paths (`generate`/`send`/`resend`/`edit` and title generation) have no tests, as do the Ollama-backed model catalog paths (`sync_models`, `download_model`, `delete_model`).
- CI has run once on `main` (run 1, conclusion success), so the ubuntu `runs-on` image, the Tauri system package list and the `src-tauri` working directory are confirmed working on that run. `README.md` carries the cargo test status badge for this workflow.
- CI uses `ubuntu-latest` (currently 24.04) instead of a pinned image, so a runner image change can alter the available Tauri packages.
- CI relies on the runner's preinstalled stable Rust toolchain; there is no `rust-toolchain.toml` or toolchain action pinning the version.
